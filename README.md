# StockSense: NovaMart demand and stock-out intelligence

**IntelliData 2026 Data Science Hackathon, Sri Eshwar College of Engineering**

> Every empty shelf is lost revenue. Can data science predict it before it happens?

StockSense forecasts the next 7 days of demand for every store x product, predicts the probability
of a stock-out, explains why, and turns that into a reorder quantity and a plain-language action
for the store manager.

## Results at a glance

| | Result |
|---|---|
| Demand forecast (Linear Regression) | **16.4% WAPE** on test weeks vs 22.2% for the brief's baseline; R² 0.935; MAE 13.2 units |
| Stock-out risk (XGBoost, calibrated) | ROC-AUC 0.796, PR-AUC 0.546, recall 60%, precision 52% |
| Action list as of 2026-08-31 | 97 high-risk, 26 medium, 159 low; 13,092 units to order; 24 overstocked items to hold |
| Business context | Rs 15.6 lakh estimated lost sales; 5.7% of store-product days end with an empty shelf |

Headline finding: **S02 Chennai grew fastest (+30%) and has the emptiest shelves**. Its reorder
levels were sized for a smaller store, which is exactly the failure a static rule cannot see.

## Quick start

```bash
pip install -r requirements.txt

# 1. See the dashboard immediately (no Python needed)
open dashboard/stocksense_dashboard.html        # or double-click it

# 2. Run the interactive Streamlit app (live what-if re-scoring)
streamlit run dashboard/app.py

# 3. Rebuild everything from raw data (about 8 minutes on a laptop CPU)
python -m src.run_pipeline
```

### Using the organisers' real data
Put the five CSVs (`transactions.csv`, `products.csv`, `stores.csv`, `inventory.csv`,
`external_factors.csv`) in `data/raw/`, replacing the synthetic ones, then run
`python -m src.run_pipeline`. Column names follow the brief. The inventory loader also
accepts the short headers from the brief's sample table (`store`, `opening`, `reorder_lvl`, ...). Date
boundaries for the splits are in `src/config.py`.

The data in `data/raw/` is **synthetic**, generated by `src/generate_data.py` to match the brief's
schemas and deliberately include all six data-quality traps (duplicates, category spelling
variants, negative quantities, inventory mismatches, missing weather, sparse new products).

## Method

**Round 1: data.** Every issue is logged with count, action and justification
(`reports/data_quality_report.md`). Transactions are aggregated to daily store x product and merged
with inventory, product, store and external tables. The **stock-out definition** is closing
stock = 0 at the end of the day. EDA answers the brief's six questions plus a weather check. Four
hypothesis tests are in `reports/statistical_tests.md`.

**Round 2: models.** Prediction happens at the end of day *t* for *t+1 ... t+7*. Features use only
data up to *t*, plus the published festival calendar. The split is **time-ordered and purged**:
train, then a 7-day gap, then validation, then a 7-day gap, then test, so training targets never
overlap evaluation days. Six regressors are compared against the brief's baseline (previous 7-day
mean x 7), and six classifiers are ranked by PR-AUC. Class imbalance is handled with class weights
and `scale_pos_weight`. The chosen classifier is **isotonic-calibrated**, so the brief's 0.70 and
0.40 bands mean real probabilities. The alert threshold maximises F2 subject to precision of at
least 45%. Only permitted algorithms are used. Full tables are in `reports/model_comparison.md`.

**Round 3: decisions.**
- Safety stock = z x daily demand std x sqrt(lead time), with z = 1.65 / 1.28 / 1.00 for High / Medium / Low.
- Recommended stock = 7-day forecast + safety stock, capped at shelf life for perishables.
- Reorder = max(0, recommended - current - incoming), rounded up to the case pack.
- **Guard-rails**: an empty shelf, or stock that runs out before a new order could arrive, is always
  High. The model cannot see open purchase orders, so it learned that empty shelves are often refilled
  soon. Each escalation is labelled as a rule, never hidden.
- **Explanations**: each business driver (promotion, festival, low cover, recent growth, lead time,
  weather...) is reset to a normal level and both models re-run. The change in prediction is that
  driver's impact, for example "Promotion running: +10 pts risk".
- **What-if**: promotion discount, supplier delay, festival and demand shock. Supplier delays change
  risk only, never demand. A promotion is modelled as a price cut against the item's recent price.

## Known limitations
1. **Censored demand.** Sales cannot exceed stock, so the target under-states demand for items
   that often stock out. Safety stock partly compensates.
2. **Festival effects are under-learned.** There are only a handful of festival days in five
   months. More history or an explicit festival multiplier would help.
3. **No open purchase orders in the data.** Incoming stock defaults to 0. Connecting the PO system
   would remove most guard-rail escalations.
4. Synthetic data. Re-run on the real files before drawing business conclusions.

## Viva preparation: questions you should be able to answer
- *Why WAPE over MAPE?* Orders are in units. MAPE explodes on slow movers (3 vs 1 is 200%).
- *Why did Linear Regression beat XGBoost?* Strong lag and rolling features make the relationship
  nearly linear. The simpler model generalised as well, and it is faster and easier to explain.
- *How do you know there is no leakage?* Rolling windows end at *t*, targets start at *t+1*, and
  there is a 7-day purge between splits. Notebook 02 recomputes one row by hand to prove it.
- *Why calibrate?* Class weighting inflates probabilities. The fixed 0.70 band only means
  "70% chance" after calibration (see `reports/figures/11_calibration.png`).
- *Why are some items High when the model said 40%?* Guard-rails: the shelf is empty, or runs out
  before a new order can arrive. Each one is labelled.
- *What would you do next?* Add open purchase orders, add more festival history, and backtest the
  reorder policy against actual lost sales.
